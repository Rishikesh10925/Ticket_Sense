# Datasheet: TicketSense Benchmark v1

Format after Gebru et al., "Datasheets for Datasets" (Blueprint ref. [19]). Owner:
Shivaganesh. Status: **frozen 2026-10-19, provisional** until the 120 KB articles are
human fact-checked (0/120 at freeze). Hashes and counts: [freeze record](../data/benchmark/FREEZE_v1.json);
check them with `python ai/benchmark/freeze.py verify --version v1`.

## Motivation

- **Purpose.** To test whether a support system can decide *when an AI-drafted reply
  deserves to be shown*. Every ticket carries known provenance, including tickets that
  cannot be answered from the knowledge base, so a trust gate can be evaluated where it
  matters.
- **Creators.** Rishikesh, Aashritha Reddy and Shivaganesh (B.Tech CSE Data Science,
  NMIMS MPSTME Hyderabad), as part of the TicketSense capstone.
- **Funding.** None.

## Composition

- **Instances.** Synthetic IT and HR support tickets (subject, body, optional pasted log)
  plus a synthetic knowledge base of 120 articles in five departments (SAP, Networking,
  Cloud, Database, HR), six topics each.
- **Size.** 1,775 tickets from 596 scenarios (target 1,800: 28 paraphrases failed every
  quality retry and were dropped rather than kept; 209 attempts were rejected and
  regenerated). 277 tickets include a pasted log.

| Type | Tickets | Share | | Department | Tickets |
|---|---|---|---|---|---|
| A | 975 | 54.9% | | SAP | 374 |
| B | 265 | 14.9% | | Cloud | 356 |
| C1 | 355 | 20.0% | | Database | 351 |
| C2 | 180 | 10.1% | | HR | 350 |
| | | | | Networking | 344 |
- **Types, by construction.**

| Type | Share | Meaning | Correct behaviour |
|---|---|---|---|
| A | 55% | Answerable from one served article | Correct, cited draft |
| B | 15% | Served article plus one extra question it cannot answer | Cautious draft or escalation |
| C1 | 20% | Written from a withheld article (6 topics, 24 articles not served) | Escalation |
| C2 | 10% | Vague, or an in-department request no article covers | Escalation or a request for information |

- **Labels.** department, priority (assigned in code before generation), type, gold
  article ids, difficulty flags (typos, vague, multi-issue, pasted log), and for B tickets
  the unanswerable question.
- **Grouping.** `group_id` identifies a scenario (one source plus one situation), whose
  three paraphrases share it. Splits use the gold article as the leakage unit
  ([split-manifest.md](split-manifest.md)).
- **Splits.** train 824, val 135, calib 262, test 271 (locked; read once in Week 10),
  unseen 283 (C1 only). Split seed 2026; manifest `data/benchmark/splits_v1.json`.
- **Missing information.** Human acceptability labels are added later (600 drafts, Weeks 7 to 8).
- **Confidential or personal data.** None. All names, systems and policies are fictional.
  Organisation-specific policies (notice periods, limits) describe a fictional company.

## Collection process

1. Topic taxonomy and withheld topics fixed in Week 1 ([data/taxonomy.yaml](../data/taxonomy.yaml)).
2. Articles written in a fixed template with AI assistance and edited by the authoring
   member; each article must then be fact-checked by a second member
   ([kb-authoring-workflow.md](kb-authoring-workflow.md)). The freeze record states how
   many were reviewed at freeze time.
3. Tickets generated by a local open-weight model (`qwen2.5:7b-instruct` via Ollama,
   temperature 0.8, fixed seeds) from a prompt that shows only the article's symptom and
   cause, never the steps. Prompt version `ticket-v2`.
4. Controls applied in code: priority and difficulty sampled with a fixed seed; typos
   injected deterministically; body length sampled from a public dataset's length
   distribution (aggregate statistics only); tickets rejected and regenerated if they copy
   a 5-word run from the article's hidden sections, or if a pasted log copies a 4-word run;
   JSON fragments filtered out.
5. Every LLM call is cached by a hash of its full input, so the benchmark regenerates
   bit for bit from the repository.

## Preprocessing

None beyond the controls above. Raw generator output is the dataset.

## Uses

- **Intended.** Evaluating confidence signals, selective prediction and risk-controlled
  gating for retrieval-grounded ticket drafts; retrieval evaluation against gold provenance.
- **Not intended.** Training production support systems; claims about real enterprise
  ticket distributions; any claim that this is real company data.

## Known limitations

- **Synthetic and easier than real data** (risk R4). Ticket phrasing comes from one 7B
  model, and paraphrases of one scenario are similar. Results show relative differences
  between methods, not production accuracy.
- **Generator leakage.** A ticket may still hint at the cause or fix in its own words,
  which the 5-word copy check cannot catch (spot check at freeze: an A ticket on SAP date
  formats says the setting is "personal, independent of Windows regional config", which
  is the article's cause). This makes type A easier; the Week 4 retrieval evaluation
  measures how much (risk R4).
- **Fact-checking.** Article accuracy depends on the human review status recorded at freeze.
- **Vague C2 tickets** can, rarely, still match a served topic. The validator cannot
  detect this; human labels can.

## Distribution and maintenance

- **Package.** `python ai/benchmark/release.py` builds `release/ticketsense-benchmark-v1.zip`:
  tickets, splits, freeze records, the 120 articles, the red-team set, this datasheet, the
  labelling rubric, a README and `SHA256SUMS`. It is built only if the freeze verifies, and
  the same inputs always give the same bytes. No labels are included yet.
- **Licence.** **To be decided** by the authors before publication (the repository has no
  licence yet).
- **Versions.** A version change (v1.1, v2) gets a new freeze record; earlier freezes are
  never edited.
