# User study kit (Week 9 preparation, run in Week 11)

Blueprint V2 §15.4 and pre-registration H4: *the AI-assisted workflow cuts median
handling time by at least 20% with no increase in accepted major errors.*

## Design

| Item | Value |
|---|---|
| Participants | 6 to 8, acting as department engineers; not TicketSense authors |
| Conditions | **Manual** (ticket and knowledge base, no AI draft) and **Workbench** (the three-lane workbench with AI drafts) |
| Within subject | Every participant does both conditions |
| Ticket sets | Set A and set B, 20 tickets each, matched by construction ([`ticket-sets.json`](ticket-sets.json)) |
| Counterbalancing | Half the participants: Manual with set A, then Workbench with set B. The other half: Workbench with set A, then Manual with set B. Alternate by sign-up order. |
| Measures | Handling time per ticket (workbench timer), final reply quality (graded blind with the [rubric](../../labelling-rubric.md)), System Usability Scale after the Workbench condition ([`sus.md`](sus.md)) |
| Analysis | Descriptive, with paired intervals; the small-sample limitation is written into the report |
| Data | Synthetic tickets only; participants recorded as P01, P02, … |

### Ticket sets

Generated by [`ai/study/study_sets.py`](../../../ai/study/study_sets.py) (seed 2026): each set
has 11 type-A, 3 type-B, 4 type-C1 and 2 type-C2 tickets and four tickets per
department. They never overlap the locked test, the 600 labelling drafts or the rubric
pilot, and no scenario appears twice. The type of each ticket is kept in
[`ticket-sets-key.json`](ticket-sets-key.json), which participants never see.

### Study tool (built in Week 11)

Participants use the `/study` screen with a `participant` account; it can open nothing
else in TicketSense.

| Step | Command or screen |
|---|---|
| 1. Create accounts and tasks | `python -m app.scripts.setup_study --participants 8` (from `backend/`). Prints each login `p01@study.local` … with a password, **once**: copy them to the facilitator sheet. Codes and orders go to `data/study/participants.json`. |
| 2. Run a session | The participant logs in and lands on `/study`: 20 tickets in the first condition, a break screen, then 20 in the second. |
| 3. Export | `python -m app.scripts.export_study` → `data/study/tasks.csv`, `grading_sheet.csv`, `grading_key.csv` |
| 4. Grade blind | A team member who did not run the sessions fills `grade` (A/M/R/W, labelling rubric) in `grading_sheet.csv`, without opening `grading_key.csv`. |
| 5. SUS | Type the paper forms into `data/study/sus.csv`: `participant,q1,…,q10` |
| 6. Analyse | `python ai/study/analyse.py` → `docs/results/study-v1.json` and `.md` |

How the screen works:

- **Manual condition:** the ticket, a reply box and a keyword search over the knowledge
  base. No draft, lane or reasons.
- **Workbench condition:** the same, plus the lane with its reasons and, unless the lane is
  escalate, the AI draft prefilled in the reply box, its evidence and its weakest claims.
  Sending the draft unchanged is recorded as `accept`, changed as `edit`, a reply without a
  draft as `write`, and the Escalate button as `escalate`.
- **Fixed stimuli:** each ticket's lane comes from the live gate (active thresholds) when
  the accounts are created, and is the same for every participant. With thresholds
  `t-judge-2` (2026-10-22): no fast lane; set A has 12 assisted and 8 escalated tickets,
  set B 14 and 6. The sets were matched on type and department, not on lane, so this
  imbalance is reported with the results.
- **Timing:** measured on the server, from when a ticket is first shown to when it is
  sent; no timer is visible to the participant. The two warm-up tickets are done outside
  the tool.

Checked on 2026-10-22 with a throwaway participant in a headless browser: every step above,
then the participant and its data were deleted.

## Session script (about 75 minutes)

1. **Welcome (5 min).** Read the consent form ([`consent.md`](consent.md)) together; the
   participant signs or declines. Explain: synthetic tickets, nothing is graded about
   them as a person, they can stop at any time.
2. **Warm-up (5 min).** Two practice tickets that are not in either set, one per condition.
3. **First condition (25 min).** 20 tickets. Work at a normal pace; accuracy matters more
   than speed. The timer runs automatically.
4. **Break (5 min).**
5. **Second condition (25 min).** The other 20 tickets in the other condition.
6. **SUS (5 min).** The ten SUS statements about the workbench.
7. **Debrief (5 min).** Two open questions: what helped most, what got in the way.
   Write the answers down verbatim.

### What the facilitator says (Workbench condition)

> "Each ticket comes with a lane. In the fast lane the system is confident; in the
> assisted lane it asks you to check the weakest claims first; an escalated ticket has
> no AI draft. You decide in every case: accept, edit, reject or escalate. The AI can be
> wrong, and you should treat it as a colleague's draft."

### What the facilitator does not do

Answer questions about whether a draft is right, hint at lanes, or comment on speed.

## Pilot (Week 9 team integration)

Run the whole session with two people who are not participants (for example, team members
of another project). Note every confusing moment; fix the kit before Week 11.
